# Rubric: is this reproduction package ready to post?

Read the whole package first (issue, repo facts, claim comment, repro report). Judge the outcome each check names, never formatting, length, or polish. Where to find each kind of evidence is in `references/evidence-guide.md`.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (OS, tool/project version, language runtime, and any setting the issue says matters, such as driver, build profile, shell), read against what the issue says it targets | The report states the versions and platform a stranger needs to place the attempt, including any variable the issue names as relevant. Fail if there is no environment record, or it omits a variable the issue says changes the behavior. A version that differs from the issue's target is a pass only if the report says so. | required |
| steps-followable | The commands/steps in the repro report, read as a stranger starting from a clean machine | Every step that produces the shown output can be re-run from the report alone (commands are exact, inputs are given or described precisely enough to recreate, such as a minimal config whose relevant parts are named, nothing depends on a private repo, private config, or unstated setup) and the step that triggers the issue is present. Fail if a step is "set up the project" with no detail, the trigger is skipped or changed, or the repro lives in something a stranger cannot access. A cannot-reproduce report passes if it gives the exact attempt. | required |
| behavior-matches-issue | The artifacts in the repro report (output, logs, error text, exit codes), read line by line against the exact symptom the issue describes | The artifact itself shows the issue's specific behavior (same error, same failure mode, same wrong output), produced with the issue's own trigger (same input/syntax/version). Fail if the artifact shows only that the program runs, shows an adjacent or different failure (graceful error instead of a crash, compile error instead of the runtime error), shows a different version's behavior without acknowledgement, or if there is no artifact. For an honest cannot-reproduce, pass if the artifacts show a real attempt at the issue's trigger. | required |
| honest-outcome | The report's stated conclusion (reproduced / not reproduced / cause) set against what its own artifacts show | Every claim is backed by something shown: a "reproduced" has the matching artifact; a cause or root-cause is either shown or marked as a hypothesis; the scope of the claim does not exceed what was tested (no generalizing to platforms or versions not tried). An evidenced cannot-reproduce that names what differed is a pass. Fail if the conclusion contradicts or outruns the artifact ("I verified" with nothing shown, a crash claimed over non-crash output, expected/actual stated backwards). | required |
| claim-specific | The claim comment, read against the issue | The claim names this issue's actual problem or file and states a concrete next step the author will take, in a modest tone. Fail if it is a +1 / me-too, interchangeable boilerplate that could be pasted on any issue, or promises a guaranteed outcome or deadline. | required |
| policy-respected | The repo-facts block's contribution/AI policy line, read against the claim comment and the repro report together | Fail only if the policy explicitly requires AI use to be disclosed and neither the claim comment nor the repro report discloses it (treat course packages as AI-assisted work); one disclosure line anywhere in the package satisfies it. A policy that only welcomes AI, asks for human understanding or responsibility, or asks that comments be in the author's own words does not require disclosure: pass if the comments read as specific first-person writing. Bug-report template items the report omits do not fail this check. | required |
| reads-as-human | The claim and repro comments as a maintainer would read them | Written in specific first-person words about this issue rather than generic filler. | preferred |

## Verdict rule

Accept if every required check passes. Reject if any required check fails. `unclear` on a required check counts as fail. Preferred checks never change the verdict. In live mode on a claim-only draft, the repro checks (env-recorded, steps-followable, behavior-matches-issue, honest-outcome) are reported as not yet applicable and left out of the verdict.
